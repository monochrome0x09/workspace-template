# 프로젝트 전체 분석

분석일: 2026-10-18 · 범위: 현재 로컬 저장소와 Git 이력

## 1. 핵심 결론

이 저장소는 실행 가능한 애플리케이션이 아니라 **파일 기반 에이전트 작업 공간 템플릿**이다. 세션 간 맥락 보존, 단일 작업 관리, 검증 및 Git 원격 보존이 핵심 목적이다 (`README.md:1-11`).

운영 규칙과 파일 역할은 잘 구분되어 있지만, 실제 프로젝트의 목표·기술 스택·실행 명령·성공 기준은 아직 작성되지 않았다 (`PROJECT.md:3-88`). 따라서 지금 평가할 수 있는 것은 템플릿의 운영 설계와 정적 구성이다. 제품 기능, 성능, 배포 준비도, 코드 품질을 판단할 구현 근거는 없다.

이번 분석 전 `TASK.md`와 `STATE.md`도 placeholder 상태였다. 분석 수행을 위해 이 두 파일만 현재 작업에 맞게 작성했으며, 프로젝트 정의나 기존 운영 정책은 임의로 확정하지 않았다.

## 2. 구성과 책임 분리

분석 시작 시 Git 추적 파일은 16개다. 이번 보고서 추가 이후에는 17개가 된다.

```text
.
├── README.md                 사용 목적·시작 방법
├── AGENTS.md                 공통 운영 규칙
├── CLAUDE.md                 AGENTS.md를 참조하는 진입점
├── PROJECT.md                장기 목표·범위·개발·Git 규약
├── TASK.md                   현재 작업 하나
├── STATE.md                  진행 상태·다음 행동·장애물
├── PLAN.md                   선택적 전체 계획
├── CHECKLIST.md              완료 점검 기준
├── .claude/
│   ├── settings.json         모델·플러그인 설정
│   └── agents/
│       ├── Explore.md        읽기 전용 탐색
│       ├── explorer.md       탐색·요약
│       ├── runner.md         테스트·빌드·린트 실행
│       └── advisor.md        조언·검토
├── docs/
│   ├── .gitkeep
│   └── decisions/.gitkeep
└── outputs/
    └── .gitkeep
```

이 트리는 분석 시작 시점의 구성이다. `outputs/project-analysis.md`는 이번 분석에서 추가되었다.

- 문서별 역할을 README에서 한 번에 확인할 수 있다 (`README.md:13-25`).
- `CLAUDE.md`는 한 줄 참조이므로 공통 규칙을 중복 관리하지 않는다 (`CLAUDE.md:1`).
- `docs/`에는 분석 시작 시 정본 자료나 결정 기록이 없고, `outputs/`에도 기존 산출물이 없었다.
- 애플리케이션 소스, 테스트 코드, 패키지 manifest·lockfile, CI 워크플로 및 배포 설정은 현재 파일 목록에 없다. 삭제되거나 누락되었다는 뜻이 아니라 현재 템플릿 범위에 포함되지 않았다는 뜻이다.

## 3. 운영 흐름 분석

### 맥락 복구와 작업 수명주기

`TASK.md → STATE.md → PROJECT.md → PLAN.md → 필요한 docs/` 순서로 읽도록 규정한다. TASK가 placeholder뿐이면 새 작업을 시작하며, 한 번 확인한 자료의 불필요한 재독도 제한한다 (`AGENTS.md:10-21`).

완료된 작업은 다음 작업 시작 전에 TASK에서 정리하고, 남길 기록은 STATE 또는 결정 문서로 옮긴다 (`AGENTS.md:61-67`). 현재 작업과 장기 정보를 분리하는 구조는 세션 인계에 유리하다.

### 검증과 영속화

완료 전에 요구사항·체크리스트·검증·상태·산출물·커밋 및 푸시를 확인한다 (`AGENTS.md:38-49`). 클라우드 세션을 전제로 중간 단위 보존과 실패 기록까지 규정한다 (`AGENTS.md:51-59`).

장점은 문서 생성만으로 완료를 선언하지 않게 한다는 점이다. 다만 실제 원격 인증이나 네트워크가 준비되었는지는 문서만으로 보장되지 않는다. Git 보존 규칙은 실행 결과와 함께 확인해야 한다.

### 승인과 범위 통제

대규모 구조 변경, 중요한 자료 삭제, 새 외부 의존성, 되돌리기 어려운 작업은 승인 대상으로 분류한다 (`AGENTS.md:76-84`). 소규모 수정에 무거운 절차를 생략할 수 있고, 별도 계획 파일 남발도 제한한다 (`AGENTS.md:69-74`). 최소 변경 원칙과 일관된다.

## 4. 에이전트 및 외부 구성

- 기본 모델과 advisor 모델은 `opus`로 지정되어 있다 (`.claude/settings.json:7-11`). 실제 사용 가능한 모델 식별자와 런타임 적용 여부는 검증하지 않았다.
- 외부 GitHub 기반 `caveman` 마켓플레이스를 등록하고 플러그인을 활성화한다 (`.claude/settings.json:2-9`). 이는 애플리케이션 패키지 의존성은 아니지만 작업 환경의 외부 의존 요소다. 해당 파일에는 버전이나 커밋 고정이 나타나지 않는다. 실제 해석 버전·캐시·접근 가능성은 미확인이다.
- `Explore`는 읽기 전용 탐색, `runner`는 실행 결과 요약을 맡고, 둘 다 `omitClaudeMd: true`를 설정한다 (`.claude/agents/Explore.md:1-17`, `.claude/agents/runner.md:1-16`).
- `AGENTS.md`는 탐색·실행은 위임하고 설계·수정·최종 리뷰는 메인에서 수행하도록 한다. 판단 근거가 된 서브에이전트 보고는 메인이 원문을 확인해야 한다 (`AGENTS.md:86-90`).

**검토 지점:** `Explore.md`와 `explorer.md`는 이름과 목적이 유사하다. 전자는 Bash 사용 제한·턴 수·보고 방식이 구체적이지만 후자는 짧은 요약 역할만 정의한다 (`.claude/agents/explorer.md:1-8`). 현재 충돌이 발생했다는 증거는 없다. 장기적으로 두 역할을 유지할 이유와 선택 기준을 명시하면 혼동을 줄일 수 있다.

**문서 표현 차이:** README는 CHECKLIST를 “수정하지 않음”으로 요약하지만 실제 지침은 Project-Specific Checks 편집 예외를 허용한다 (`README.md:23`, `AGENTS.md:34`, `CHECKLIST.md:5`). 사용 시 상세 규칙을 함께 확인하는 편이 명확하다.

**주의:** `omitClaudeMd: true`인 에이전트에 어떤 상위 지침이 전달되는지는 실제 런타임 실험 전에는 단정할 수 없다. 위임 메시지에 작업 범위·수정 금지·보고 규칙을 명시하는 운영이 필요하다.

## 5. 현재 준비도

| 영역 | 확인 결과 | 해석 |
|---|---|---|
| 목적·시작 안내 | README에 존재 | 템플릿 사용법을 파악하기 쉽다 |
| 작업 규칙 | 구체적인 공통 지침 존재 | 역할·완료·보존 절차가 강점 |
| 실제 프로젝트 정의 | PROJECT가 placeholder/TBD | 대상 프로젝트 착수 전 작성 필요 |
| 계획 | PLAN이 단계명·작업 placeholder | 일정이나 구현 순서를 나타내지 않음 |
| 상태 인계 | 시작 시 TASK·STATE가 placeholder | 이전 실제 작업이나 완료 이력 근거 없음 |
| 코드·의존성·실행 명령 | 구현 파일 없음, 명령은 TBD | 실행 가능한 제품으로 평가할 단계 아님 |
| 자동 검증·배포 | 테스트·CI·배포 설정 없음 | 문서 템플릿이므로 그 자체를 결함으로 단정하지 않음 |
| 근거 자료 | docs에 .gitkeep만 존재 | 도메인 사실·설계 결정 검증 자료 없음 |
| Git 운영 | 작업 브랜치 및 origin 존재 | 원격 보존은 푸시 결과로 별도 확인 |

## 6. 개선 우선순위 — 제안이며 미실행

### 우선 1: 사용 방향 결정

템플릿 자체를 유지하는 저장소인지, 실제 프로젝트를 시작할 공간인지 결정한다. 현재 자료로는 어느 쪽인지 확정할 수 없다. 실제 프로젝트라면 `PROJECT.md`의 목표·범위·제약·성공 기준을 먼저 구체화하는 것이 적절하다.

### 우선 2: 실행 가능한 운영 정보 확정

개발 프로젝트로 정해졌을 때만 기술 스택과 설치·실행·테스트·린트·빌드 명령을 작성한다 (`PROJECT.md:41-61`). 작은 작업에는 PLAN을 강제로 채우지 않아도 된다 (`PLAN.md:1-3`). Git 브랜치·푸시·메시지 규약도 확정하면 현재의 TBD 대체 규칙 의존을 줄일 수 있다 (`PROJECT.md:69-74`).

### 우선 3: 환경 재현성과 위임 명확화

외부 플러그인 버전 관리 방식, 모델·설정 필드 지원 여부, 신규 환경에서의 재현 절차를 확인한다. Explore와 explorer의 선택 기준도 검토한다. 본 분석에서는 설치나 설정 변경을 하지 않았다.

### 우선 4: 필요에 맞춘 가벼운 검증 자동화

템플릿 유지가 목적이라면 JSON 구문, 필수 파일, 문서 참조 등을 검사하는 작은 검증부터 고려할 수 있다. 실제 개발 프로젝트로 전환한다면 그 프로젝트의 테스트·CI를 선택한다. 구현이 없는 지금 임의의 프레임워크나 빌드 체계를 추가할 근거는 없다.

## 7. 검증 범위 및 한계

- 로컬 문서·설정과 Git 추적 목록·이력을 근거로 분석했다. 외부 자료를 근거로 기능이나 호환성을 추정하지 않았다.
- 주요 판단의 파일 근거는 메인에서 직접 열어 확인했다.
- 애플리케이션 테스트·빌드·린트는 대상 코드와 실행 명령이 없어 적용 대상이 아니다. 이는 테스트 통과를 뜻하지 않는다.
- 별도 정적 검증으로 설정 JSON 구문, 필수 파일, 보고서 경로·줄번호 참조, Git 공백 오류를 점검한다. 실제 결과는 STATE와 최종 응답에 기록한다.
- 플러그인 설치·실행, 모델 라우팅, GitHub 저장소의 Template 설정, 원격 기본 브랜치 및 외부 서비스 상태는 검증하지 않았다.
- 분석 시작 시 작업 트리는 깨끗했으며 브랜치는 `monochrome0x09/merrow`였다. 확인한 최근 커밋은 `c1e005f`(2026-10-10)이고, 에이전트 역할 규칙을 AGENTS로 옮긴 변경이었다. 로컬 이력은 원격 최신 상태를 보장하지 않는다.

## 종합 평가

**운영 규칙은 구체적이지만, 실제 프로젝트 내용은 아직 비어 있는 출발용 템플릿이다.** 현재 필요한 것은 코드 리팩터링보다 사용 목적 확정과 프로젝트 정보 구체화다. 템플릿 자체를 개선한다면 역할 중복 정리, 환경 재현성, 가벼운 문서 검증이 우선 검토 대상이다.
